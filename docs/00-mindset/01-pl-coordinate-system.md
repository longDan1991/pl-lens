# 0.1 为什么你的直觉在系统语言里全线失效？

> **副标题**：六门语言的 PL 坐标系：运行时、内存与抽象成本全景

如果你长期写 TypeScript 和 Python，第一次切到 Rust 或 C++，大概率会有一种强烈的割裂感：明明只是想把一个对象传给另一个函数、或者建一个互相引用的图结构，怎么编译器处处报错，或者一跑起来就段错误（Segmentation Fault）？

**问题不在你语法没背熟，而在你脑子里的「默认心智模型」换了底盘。**

TS 和 Python 给你提供了一层厚厚的**托管运行时（Managed Runtime）**：所有对象默认住在堆上，变量只是指向堆对象的引用，GC 替你兜底生命周期，类型大多在运行期或编译后擦除。而 Rust 和 C++ 的第一性原理是**零成本抽象（Zero-Cost Abstraction）**——你写的每一行代码，都直接对应到机器内存布局和 CPU 指令。

---

## 一、底层机制与跨语言对照：6 门语言的 PL 坐标系

不要按语言孤立背特性。从编程语言理论（PL）视角看，主流工业语言的分歧只集中在 **7 个正交维度** 上：

| PL 维度 | TypeScript | Python | Go | C | Rust | C++ |
|---|---|---|---|---|---|---|
| **内存管理** | Tracing GC (V8) | 引用计数 + 循环 GC | 逃逸分析 + 三色标记 GC | 手动 (`malloc`/`free`) | 编译期所有权 / 借用检查 | 手动 + RAII / 智能指针 |
| **默认语义** | 对象引用语义 / 原始值语义 | 一切皆堆对象引用 | 值语义（含显式指针） | 值语义（裸指针） | 值语义 + 默认 Move | 值语义 + 默认 Copy |
| **类型检查** | 静态（编译后完全擦除） | 动态（运行期检查） | 静态强类型（无隐式转换） | 静态弱类型（允许强转） | 静态强类型 + 局部推导 | 静态强类型（隐式转换多） |
| **类型等价** | Structural（结构化） | Duck Typing（运行期） | 接口 Structural / 其余 Nominal | Nominal（名义化） | Nominal（名义化） | Nominal（名义化） |
| **泛型实现** | 类型擦除 | 运行期统一 `PyObject*` | 字典 + GC Shape 单态化 | 宏 / `void*` | 编译期完全单态化 | 编译期模板实例化（单态化） |
| **多态派发** | 原型链 / Hidden Class | 属性字典（动态） | Interface 胖指针（运行期） | 手动函数指针 | 静态派发 / `dyn` 胖指针 | 模板静态派发 / `vptr` 虚表 |
| **错误处理** | 异常 (`throw`) | 异常 (`raise`) | 多返回值 `error` | 错误码 / `errno` | 代数类型 `Result<T, E>` | 异常 / `std::expected` |

### 三个让你「浑身难受」的根本断层

#### 断层 1：引用语义 vs 值语义（`b = a` 到底发生了什么？）

在 Python / TS 里，给对象赋值几乎零心智负担——你只是复制了一个指针。但在系统语言里，`b = a` 必须明确回答：**内存是浅拷贝、深拷贝，还是所有权转移？**

::: code-group

```ts [TypeScript]
// a 和 b 指向堆上同一个数组对象，修改 b 会影响 a
const a = [1, 2, 3]
const b = a
b.push(4) // a 现在也是 [1, 2, 3, 4]
```

```python [Python]
# 同上：a 和 b 绑定同一个 PyListObject*，引用计数 +1
a = [1, 2, 3]
b = a
b.append(4)  # a 也是 [1, 2, 3, 4]
```

```cpp [C++]
#include <vector>

std::vector<int> a = {1, 2, 3};
std::vector<int> b = a;            // 默认深拷贝！触发一次堆分配 + 逐元素复制
std::vector<int> c = std::move(a); // 显式移动：仅转移内部指针/长度/容量，a 变为空壳
```

```rust [Rust]
let a = vec![1, 2, 3];
let b = a;          // 默认 Move！只拷贝栈上 24 字节头，a 立刻失效（编译期防 UAF）
// println!("{:?}", a); // 编译错误：borrow of moved value: `a`
let c = b.clone();  // 深拷贝必须显式写出，绝不暗中花钱
```

:::

**关键洞察**：
- **C++ 默认深拷贝**：最容易在不经意间（比如函数按值传参 `void f(std::vector<int> v)`）触发隐式堆分配，拖垮性能。
- **Rust 默认 Move**：把“浅拷贝头 + 旧变量失效”做成默认行为，强迫你把昂贵的 `.clone()` 显式暴露在代码里。

#### 断层 2：静态语义 vs 运行期表示（TS 类型为何“不占内存”？）

TypeScript 的类型系统表达能力极强（甚至图灵完备），但它**只活在编译期**，生成 JS 后被彻底擦除。V8 引擎在运行期看到的依然是动态对象，必须靠 Hidden Class 和内联缓存（IC）去猜测内存布局。

而在 C / C++ / Rust 中，**类型直接决定了字节布局**：
- 一个 `struct Point { x: f64, y: f64 }` 在内存中就是紧挨着的 **16 个字节**，没有对象头（Object Header），没有 GC 标记位，没有属性哈希表。
- 存 100 万个 `Point`：
  - **Rust / C++ `Vec<Point>` / `std::vector<Point>`**：一整块连续的 `16 MB` 内存，CPU 预取器拉满。
  - **Python `list[Point]`**：一个存放 100 万个指针的数组 + 100 万个分散在堆上的 `PyObject`（每个对象还要带引用计数、类型指针、`__dict__`），轻松膨胀到 **100 MB+** 且满地缓存未命中（Cache Miss）。

#### 断层 3：泛型擦除 vs 编译期单态化（Monomorphization）

当你写一个泛型函数 `fn max<T: Ord>(a: T, b: T) -> T`：
- **TS**：编译后擦除 `<T>`，只剩一份 JS 函数。
- **Rust / C++**：如果你分别用 `i32` 和 `f64` 调用它，编译器会生成**两份完全独立的机器码**（`max_i32` 和 `max_f64`），并直接内联进调用点。代价是**编译变慢、二进制体积变大**；收益是**零运行期派发开销**。

## 二、工程落地与踩坑：切到系统语言的 4 条心智切换清单

在真正写 Rust / C++ 工程代码前，先用这 4 条规则覆盖掉 TS/Python 留下的肌肉记忆：

1. **看见 `=` 和函数传参，先问一句“拷贝了多少字节？”**
   - C++ 里非平凡类型默认传 `const T&` 或 `std::string_view` / `std::span`，绝不随手按值传 `std::string` / `std::vector`。
   - Rust 里默认传借用 `&T` / `&str` / `&[T]`，只在需要接管生命周期时才传拥有权 `T`。
2. **区分“栈上扁平数据”和“堆上间接指针”**
   - 在 TS/Python 里 `a.b.c` 每次 `.` 都可能是一次指针解引用；在 Rust/C++ 里尽量把高频访问的数据打平放进连续数组（`Vec<T>` / `std::vector<T>`），减少指针跳转（Pointer Chasing）。
3. **放弃“先写出来再让 GC 擦屁股”的图状数据结构**
   - 双向链表、父子互相引用的树、循环图在 GC 语言里随手写；在系统语言里，它们不仅在 Rust 会触发借用检查器地狱，在 C++ 也极易引发悬垂指针与缓存抖动。工业界首选**连续数组 + 整数索引句柄**（第 2 章详讲）。
4. **把编译报错当成免费的代码审查**
   - C++ 编译器对未定义行为（UB）非常宽容，能过编译不代表没炸弹；Rust 编译器把很多运行期隐患前移成编译错误，前期憋屈，换来的是线上少熬通宵。

## 三、面试连环追问 Q&A

### Q1：TypeScript 和 Rust 都是静态强类型，为什么 TS 的性能远不如 Rust？

- **结论**：静态类型检查只决定“编译期能不能抓错”，真正决定性能的是**类型信息是否下沉为运行期内存布局与单态化机器码**。
- **原理**：TS 的类型在转译为 JS 时完全擦除，运行期 V8 仍需处理动态对象头、装箱/拆箱、GC 追踪和 JIT 猜测（去优化 Deopt 会直接掉性能）；Rust/C++ 利用静态类型在编译期确定精确的字节偏移（offset）、无装箱连续内存布局，并通过单态化消除抽象与间接调用，直接生成针对寄存器优化的原生指令。
- **权衡**：TS 换取了极快的开发迭代与浏览器/Node 生态；Rust/C++ 用更长的编译时间、更严苛的内存约束换取可预测的极致性能。

### Q2：Rust 的默认 Move 和 C++ 的默认 Copy，各自在工程上带来什么代价？

- **结论**：C++ 的默认 Copy 隐蔽了性能成本，Rust 的默认 Move 提高了心智与语法摩擦，但消灭了隐式拷贝和 Move 后误用（Use-After-Move）。
- **原理**：C++ 为兼容 C 值语义，拷贝构造函数默认隐式触发，且 `std::move` 后源对象处于“有效但未指定状态”，编译器不禁止继续读取；Rust 对非 `Copy` 类型默认执行按位浅移（bitwise move）并在编译期静态废止原绑定，深拷贝必须显式 `.clone()`。
- **权衡**：现代 C++ 工程通常通过 `= delete` 禁用大对象拷贝构造函数，或借助 Clang-Tidy 检查隐式拷贝来弥补这一风险。

### Q3：为什么在系统语言里，“结构化类型（Structural Typing）”很少被用于核心数据结构？

- **结论**：结构化子类型难以在不引入动态查表或胖指针的前提下，保证零成本的固定内存偏移访问。
- **原理**：如果两个结构不同、字段顺序不同的对象只要“都包含字段 `x`”就能传给同一个函数，运行期就必须知道 `x` 在当前对象里的偏移量——这要么靠动态哈希表（Python）、Hidden Class（V8），要么靠接口胖指针（Go `interface`）。而名义类型（Nominal Typing）配合单态化，允许编译器把 `p.x` 直接编译成一条固定偏移的基址寻址指令（如 `[rdi + 8]`）。
- **补充**：Rust 的 Trait 和 C++20 的 Concepts 通过**编译期约束 + 单态化**，在保持零运行期开销的同时，部分模拟了结构化接口的灵活性。
